# Shaka v0.7.0 — implementação da Etapa A

**Status:** implementada localmente na branch `roadmap/v0.7.0`

## Entregas

A Etapa A criou a fundação de observabilidade no crate `shaka-observability` sem integrar ainda métricas/exporters aos componentes HTTP, fila ou runtime.

| Componente | Implementação |
|---|---|
| `Telemetry` | Fachada com política estrita, schema `shaka.observability` v0.7, perfil `shaka.genai.v0.7`, criação de contexto e span inicial |
| `CorrelationContext` | Request ID validado e referências opcionais de trace, span, tarefa, sessão e tenant redacted |
| `Redactor` | Redaction de texto, metadata e JSON recursivo; limites de caracteres, profundidade e itens; bloqueio de conteúdo sensível |
| `AuditLogger` | Integração do redactor antes da persistência de metadata textual e JSON, preservando as assinaturas existentes |
| Testes | Sete testes unitários de política, redaction, JSON, campos, correlação, spans e limites |
| Versão | Workspace e lockfile alinhados para `0.7.0` |
| Documentação | `V0.7_DESIGN.md` e `CHANGELOG.md` atualizados |

## Garantias de segurança

A captura de prompts, respostas e argumentos de ferramentas é rejeitada pela política padrão. Padrões de bearer token, API key, authorization, cookie, secret, password, private key e tokens são redacted. JSONs aninhados também são tratados por nome de chave e por conteúdo textual. Limites de tamanho, profundidade e cardinalidade estrutural impedem crescimento ilimitado de dados de telemetria.

O redactor não depende de `expect` ou `unwrap` em runtime. Falha de compilação da expressão regular interna degrada para o texto original somente como fallback técnico do literal estático; a expressão é validada pelos testes de redaction. O `AuditLogger` permanece compatível com a v0.6.0, mas agora protege metadata antes de criar o `AuditEvent` hash-chained.
