# Plano de manutenção v0.8.1 do Shaka

## Decisão pós-release

A release v0.8.0 está aprovada para **operação local controlada em dry-run**. A validação confirmou CLI, configuração, `doctor`, auditoria, sandbox, backup, restauração, API loopback, worker, conclusão de tarefa e replay idempotente. O bloqueio de `live` para operador comum também foi confirmado.

Esta decisão não representa autorização para exposição pública, execução de efeitos externos ou ampliação da autoridade do agente. A tag v0.8.0 permanece imutável.

## Objetivo

A v0.8.1 deve ser uma release de manutenção. Seu objetivo é reduzir dívida documental e ruído operacional, consolidar a experiência de instalação e fortalecer testes sem alterar o modelo de segurança ou liberar novas capacidades.

## Escopo recomendado

| Tema | Entrega | Critério de aceite |
|---|---|---|
| Documentação | Atualizar o estado do `README.md` para v0.8.0 e substituir exemplos históricos de release | Nenhuma instrução de uso aponta para versão antiga ou contradiz a CLI atual |
| Runbook | Incorporar o runbook v0.8.0 ao fluxo documental rastreado | Operador consegue validar, executar dry-run, fazer backup e investigar falha |
| Warnings | Revisar avisos de documentação ausente do build release | Redução dos warnings públicos sem alterar comportamento |
| CI/CD | Avaliar atualização das actions que geraram warning de Node.js 20 | Workflow permanece verde e sem warnings evitáveis |
| Testes | Adicionar matriz de crash/restart, backup/restore e concorrência | Cenários críticos reproduzíveis automaticamente |
| API | Melhorar mensagens e documentação de health check/idempotência | Contrato documentado e smoke test estável |
| Container | Adicionar smoke test documentado para hosts com Docker | Execução local em loopback e healthcheck reproduzíveis |

## Fora do escopo

A v0.8.1 não deve habilitar `live`, mensageria externa, pesquisa autônoma, autopromoção de skills, autoevolução, subagentes irrestritos, IAM remoto, escala horizontal ou qualquer mecanismo que aumente autoridade sem revisão independente.

## Critérios de entrada

O trabalho só deve iniciar após preservar a tag v0.8.0, manter o working tree limpo de artefatos temporários e criar uma branch de manutenção a partir do commit publicado em `main`. Relatórios locais de auditoria não devem ser adicionados automaticamente ao repositório.

## Critérios de saída

A v0.8.1 só deve ser considerada pronta quando `cargo fmt --check`, `cargo check --workspace --locked`, testes, Clippy, secret scan, workflow policy, cargo audit, smoke test de produção, build release, geração de SBOM, checksums e container forem verdes. O resultado deve ser revisado antes de qualquer nova tag ou publicação.

## Sequência recomendada

Primeiro, corrigir a documentação de versão e consolidar o runbook. Depois, revisar warnings e actions do CI. Em seguida, ampliar a matriz de testes de falha e concorrência. Por fim, repetir a validação da release e preparar os artefatos de manutenção.

Nenhuma operação definitiva no GitHub, incluindo commit publicado, merge, tag ou release, faz parte deste documento. Essas ações só devem ser realizadas após revisão e confirmação explícitas.
