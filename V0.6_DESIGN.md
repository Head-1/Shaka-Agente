# Shaka v0.6.0 — IAM multiusuário e autorização contextual

**Status:** desenho aprovado para implementação  
**Versão-alvo:** `0.6.0`  
**Base:** Shaka v0.5.0, produção candidata para operação controlada

## 1. Objetivo

A v0.6.0 substitui o principal único configurado no processo por uma camada de identidade persistente e verificável. A API continuará funcionando em loopback por padrão, mas passará a resolver o principal por token bearer opaco armazenado somente como hash no SQLite. Cada usuário pertence a um tenant, possui papel explícito, pode estar revogado e está sujeito a quotas e rate limits aplicados pelo host.

O modelo continua sem autoridade para autenticar, criar tenants, alterar papéis, conceder capabilities ou elevar quotas. A mudança adiciona identidade e autorização ao host; não habilita autoevolução, aprovação automática de skills, web, mensageria ou execução live por padrão.

## 2. Escopo

A entrega implementará:

| Área | Entrega |
|---|---|
| Identidade | Usuários persistentes, tenants persistentes e tokens bearer opacos com hash SHA-256. |
| Autenticação | Resolver o principal por `Authorization: Bearer`; suporte de compatibilidade para API key estática local. |
| Autorização | RBAC por ação e autorização contextual por tenant, papel, estado do usuário e recurso. |
| Sessões | Sessão vinculada ao principal autenticado que a criou; acesso posterior exige tenant e operador compatíveis. |
| Quotas | Limites por tenant para tarefas ativas, tarefas diárias e custo diário. |
| Rate limit | Janela fixa persistente por tenant e por operador para submissões e consultas sensíveis. |
| Administração | CLI para criar tenant, criar usuário, emitir/revogar token e consultar quotas. |
| Auditoria | Eventos de emissão, revogação, autenticação negada, quota excedida e rate limit excedido. |
| Compatibilidade | API REST v1 preservada; clientes locais existentes continuam funcionando com a API key configurada. |

Ficam fora desta entrega: OIDC/OAuth2 remoto, verificação JWT assimétrica, PostgreSQL, coordenação de múltiplas réplicas, quotas distribuídas, Plan Engine, OpenTelemetry OTLP completo, pesquisa web e mensageria.

## 3. Modelo de confiança

O token bruto nunca é persistido nem gravado em logs. A emissão devolve o token uma única vez. O banco armazena `SHA-256(token)`, prefixo público para identificação operacional, principal, criação, expiração opcional, revogação e último uso. A autenticação compara o hash em consulta parametrizada.

A autorização usa o seguinte contexto:

```text
AuthenticatedPrincipal {
    principal: Principal,
    token_id: String,
    authenticated_at: DateTime<Utc>,
    source: Token | StaticApiKey,
}
```

O cliente nunca fornece `tenant_id`, `operator_id` ou `role` para formar o principal. Esses campos vêm exclusivamente do registro autenticado. Um usuário revogado ou um token expirado falha com `401` antes de tocar sessões ou tarefas.

## 4. Esquema persistente

As migrações são idempotentes e preservam todos os dados v0.5.0:

```sql
CREATE TABLE IF NOT EXISTS api_tenants (
    tenant_id TEXT PRIMARY KEY,
    display_name TEXT NOT NULL,
    active INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS api_users (
    operator_id TEXT PRIMARY KEY,
    tenant_id TEXT NOT NULL REFERENCES api_tenants(tenant_id),
    role TEXT NOT NULL,
    active INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS api_tokens (
    token_id TEXT PRIMARY KEY,
    token_hash TEXT NOT NULL UNIQUE,
    token_prefix TEXT NOT NULL,
    operator_id TEXT NOT NULL REFERENCES api_users(operator_id),
    created_at TEXT NOT NULL,
    expires_at TEXT,
    revoked_at TEXT,
    last_used_at TEXT
);

CREATE TABLE IF NOT EXISTS api_tenant_limits (
    tenant_id TEXT PRIMARY KEY REFERENCES api_tenants(tenant_id),
    max_active_tasks INTEGER NOT NULL,
    max_daily_tasks INTEGER NOT NULL,
    max_daily_cost_microunits INTEGER NOT NULL,
    requests_per_window INTEGER NOT NULL,
    window_seconds INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS api_rate_windows (
    scope_key TEXT NOT NULL,
    window_start TEXT NOT NULL,
    request_count INTEGER NOT NULL,
    PRIMARY KEY(scope_key, window_start)
);
```

A migração deve bootstrapar o principal configurado na v0.5.0 como tenant, usuário e token somente quando um token persistente ainda não existir. A API key estática continua sendo uma via explícita de compatibilidade local, mas não é usada para autenticar usuários distintos.

## 5. Quotas e rate limits

A submissão de tarefa aplica, na mesma transação de criação, os limites de tarefas ativas, tarefas diárias e custo diário estimado pelo envelope. O contador de tarefas só é incrementado quando uma nova tarefa é realmente criada; repetição idempotente não consome nova quota.

O rate limit usa janela fixa baseada em UTC e chave de escopo. A submissão usa simultaneamente `tenant:{tenant_id}:submit` e `operator:{operator_id}:submit`. O limite é rejeitado com `429 Too Many Requests` e header `Retry-After`. Consultas de estado usam um limite separado mais permissivo.

Quotas são fail-closed: se a leitura transacional de limites falhar, a nova submissão é recusada como erro interno e não executada sem controle. O rate limit não é um mecanismo de segurança isolado; autenticação e autorização sempre ocorrem antes dele.

## 6. Rotas administrativas da CLI

```text
shaka iam tenant create <tenant_id> <display_name>
shaka iam user create <operator_id> --tenant <tenant_id> --role operator|reviewer|administrator
shaka iam token issue <operator_id> [--expires-in-seconds N]
shaka iam token revoke <token_id>
shaka iam limits set <tenant_id> --max-active N --max-daily N --max-cost-microunits N --requests N --window-seconds N
shaka iam list
```

A saída de `token issue` exibe o segredo bruto apenas no terminal e inclui instrução explícita para armazená-lo em cofre. Logs, auditoria e `doctor` exibem somente `token_id` e `token_prefix`.

## 7. API e erros

As rotas v1 existentes não mudam. A autenticação passa a ser aplicada por request, com exceção de `/healthz`, que continua público e não revela dados de tenant. Novos códigos lógicos:

| HTTP | Código | Semântica |
|---:|---|---|
| 401 | `unauthorized` | Token ausente, inválido, expirado ou revogado. |
| 403 | `forbidden` | Principal autenticado sem ação ou recurso permitido. |
| 404 | `not_found` | Recurso inexistente ou não visível no tenant do principal. |
| 429 | `rate_limited` | Janela de requests excedida; inclui `Retry-After`. |
| 429 | `quota_exceeded` | Quota de tarefas ativas, diárias ou custo excedida. |

A resposta de erro mantém `request_id`. O servidor não diferencia, para recursos de outro tenant, entre inexistência e ausência de visibilidade.

## 8. Compatibilidade e segurança

A API key estática só pode ser usada quando configurada explicitamente. Para bind não local, a configuração deve exigir `SHAKA_API_KEY` ou a presença de pelo menos um token persistente administrado. A chave estática não pode criar ou emitir tokens pela API.

O conteúdo de objetivos e metadados continua sujeito a limites e redaction. Nenhum header de autenticação é persistido. Eventos de autorização registram ação, resultado, tenant, operador e token_id, sem segredo.

## 9. Critérios de aceite

A v0.6.0 será aceita quando houver testes para criação e revogação de tokens, expiração, isolamento entre tenants, acesso cruzado negado, RBAC por ação, bootstrap de compatibilidade, quota de tarefas ativas, quota diária, quota de custo, rate limit de tenant e operador, idempotência sem consumo duplicado, `401`, `403`, `404`, `429`, migração de banco v0.5.0 e auditoria redacted.

Os gates existentes permanecem obrigatórios: fmt, check, test, Clippy estrito, secret scan, workflow policy, auditoria de dependências e smoke test HTTP. A versão do workspace, changelog, documentação, Docker e workflows deve ser atualizada para `0.6.0` sem alterar o bind loopback ou o default dry-run.

## 10. Evoluções seguintes

A v0.6.1 poderá adicionar um contrato canônico de provider e o Plan Engine com planos persistentes. A v0.6.2 deverá adicionar o Eval Harness. A v0.7.0 adicionará OpenTelemetry GenAI, métricas, traces, SLOs e alertas. A migração para IAM remoto OIDC/OAuth2 e PostgreSQL fica preparada por traits e contratos, mas não é simulada pela v0.6.0.
